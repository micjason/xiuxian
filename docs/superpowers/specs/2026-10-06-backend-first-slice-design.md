# 后端第一批设计

- 日期：2026-10-06
- 状态：已确认，按此写实施计划
- 相关：ADR-0006

这一批只做本机可运行的后端。不连 `101.132.74.32`，不做后台页面，不改手机客户端。

## 已经确定的选择

- 会改进度的操作，成功和失败都留记录。动作包括登录、结算、突破、发布、修复。
- 修旧数据用固定程序：先预览，确认后写入，同一玩家对同一程序只生效一次。
- 操作记录进数据库。进程崩溃、来不及入库的错误另写日志文件。
- 代码按业务分块。结算、突破、战力是纯规则，不依赖网页接口。
- 约定写成一条始终生效的项目规则，加上一个写后端时才用的技能。
- 第一批包含玩法接口、操作记录的写入和查询、修复入口。第一批不预置任何真实修复程序。

## 结构

一个 TypeScript + Fastify 进程，本机 PostgreSQL。五块业务：

| 块 | 负责 |
|---|---|
| 登录 | 玩家注册和登录。管理员单独登录。两边的会话不能混用 |
| 玩家进度 | 打开时结算、突破、返回战力 |
| 配置发布 | 境界、技能、物品的草稿，以及发布。同时只有一份草稿和一份当前已发布版本 |
| 操作记录 | 写入，并按玩家名和时间查询 |
| 修复 | 预览名单、按名单编号确认写入 |

密码用 argon2id 哈希。登录成功后发一个服务器保存的会话编号。会话表不保存明文令牌。玩家会话调用管理接口时拒绝。管理员没有公开注册接口，第一个管理员用本机命令创建。

表结构用 TypeScript 描述，实际执行的 SQL 由工具按差异生成并留在仓库里。

## 一次结算

玩家带着会话请求进度。服务器只认会话对应的玩家，不采用请求里的修为、境界或战力。

同一次数据库事务里：

1. 锁住该玩家的进度行。
2. 读出修为、境界编号、上次结算的服务器时间。
3. 只读当前已发布配置，取出该境界的每秒修为和离线上限。
4. 用服务器当前时间减去上次结算时间。超过上限的秒数不算。
5. 纯规则算出新修为。战力按当前已发布配置现算，不写入进度。
6. 写回修为和这次结算时间，并写一行成功的操作记录。

事务成功后返回境界名、修为、战力和本次增加量。境界名来自已发布配置，进度里只存境界编号。

规则判定不能结算时，进度不变，另写一行失败记录。数据库在提交过程中失败时，进度和记录一起不留。来不及入库的崩溃写入日志文件。

突破和发布使用同一套做法：规则先算，进度或配置与成功记录在同一次事务里提交。

## 操作记录

一行只记这一次操作的结果，不记完整请求。密码、明文会话和令牌不进入记录，也不进入崩溃日志。

| 字段 | 内容 |
|---|---|
| 时间 | 服务器时间 |
| 谁 | 玩家或管理员，含编号和当时的名字 |
| 动作 | 登录、结算、突破、发布、修复 |
| 结果 | 成功，或失败及原因 |
| 配置版本 | 这次使用的已发布版本。发布动作记新版本编号 |
| 前后数值 | 只留和这次动作有关的数 |

前后数值：

- 登录成功记玩家编号。失败记尝试的用户名和原因，不记密码。
- 结算记修为前后、经过的秒数、每秒修为、境界编号。
- 突破记境界前后、消耗、修为前后。失败记当时修为和原因。
- 发布记上一版编号和新版本编号。
- 修复记程序名、影响人数和摘要。

管理员按玩家名、开始时间和结束时间查询。名字是操作发生时写下的名字。可以再限定动作，例如只看结算或只看失败。查询发布时不填玩家名，只按时间和动作「发布」。

崩溃日志写在本机 `backend/var/crash.log`。该目录不进入 Git。

## 修复入口

每个修复程序有固定名字。预览只读操作记录和当前进度，算出谁会被改、改前和改后的值，不写进度。

预览存成一份名单并给出编号。确认时必须带上这个编号，写入的就是这份名单上的数。确认前相关进度变了，确认失败，需要重新预览。

写入在一次事务里完成。同一玩家对同一个修复程序只保留一行生效记录，第二次写入被拒绝。已处理的人在新预览里标为已处理。写完追加一行修复操作记录。

未知程序名的预览直接失败。第一批没有真实修复程序。测试注册一个假程序，证明预览不写数据、确认后写入、再次确认不会改第二次。

## 规则和技能

实现开始时新增始终生效的规则，句子如下：

- 修为、境界、战力、突破由服务器计算。请求里带来的这些数不能写入进度。
- 登录、结算、突破、发布、修复，成功和失败都写入操作记录。记录里有谁、服务器时间、配置版本、前后数值、失败原因。密码和令牌不写进记录，也不写进崩溃日志。
- 进度和对应的成功记录在同一次数据库事务里写入。事务失败则两边都不留。
- 修旧数据只走具名修复程序：先预览名单，确认那份名单的编号后才写入。同一玩家对同一个修复程序只生效一次。
- 玩家会话不能调用发布、查询记录、预览修复和确认修复。

同时新增后端技能，写后端时按这个顺序：

1. 新业务放在自己的一块里。结算、突破、战力是纯规则，测试时不启动网站。
2. 接口只接收请求、调用规则、写入数据库。修数据的程序不写进结算接口。
3. 会改进度或配置的操作，补上操作记录的测试：成功有前后数值，失败有原因且进度不变。
4. 修复程序补三个测试：预览不写数据，确认后写入，再执行一次不会改第二次。
5. 玩家会话调用管理接口的测试必须失败。

## 第一批不做

- 后台网页、手机客户端、部署到已购买的服务器。
- Redis、玩家运营、活动运营。
- 具体的某一条真实修复逻辑。
- 把归档配置一键复制回草稿。

## 验证

用本机 PostgreSQL 和自动化测试证明：

- 保存草稿后，玩家进度接口仍返回发布前的名字和每秒修为。
- 发布成功后，再次结算使用新数值，玩家身上的境界编号不变。
- 两次同时打开不会把同一段时间结算两遍。
- 名称为空或编号重复时发布失败，已发布版本不变。
- 结算失败时进度不变，且能按玩家名查出失败原因。
- 假修复程序的预览不写数据，确认后写入，再次确认不改第二次。
- 玩家会话调用发布、查询记录和修复接口时被拒绝。
