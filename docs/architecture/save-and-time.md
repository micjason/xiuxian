# 存档与离线时间设计

## 目标

设备断电、写入中断、应用升级和内容更新不得轻易破坏玩家进度。离线收益必须可测试、可迁移且由一个时间入口计算。

## 存档信封

业务数据外层至少记录：

```json
{
  "schema_version": 2,
  "app_version": "0.1.0",
  "content_version": "0.1.0",
  "saved_at_unix": 0,
  "payload": {},
  "checksum": ""
}
```

`payload` 只保存不能可靠重算的玩家状态。`schema_version` 2 起还包括行囊、穿戴、已学功法、当前关卡、战报种子与设置。缓存、界面滚动位置和可由配置推导的数据不进入存档。v1 旧档在加载时补上历练默认值。

## 写入流程

1. 从领域状态生成快照，不直接序列化场景节点。
2. 校验字段、范围和引用的配置 ID。
3. 写入同目录临时文件并确保完整落盘。
4. 重新读取并校验临时文件。
5. 将当前有效存档轮换为备份，再原子替换正式文件。
6. 记录成功时间；失败时保留原有效存档。

启动加载依次尝试正式存档、备份和安全的新档流程。自动恢复必须记录原因并告知用户，不静默覆盖异常数据。

## 迁移

- 每次格式变化递增 `schema_version`。
- 迁移函数只处理相邻版本，例如 `v1 → v2 → v3`。
- 迁移前保留原文件；迁移后执行完整校验。
- 测试至少包含最老受支持版本、上一版本、当前版本、损坏文件和未知新版本。
- 无法理解更高版本存档时拒绝降级写回，避免永久损坏。

## TimeService

所有功能依赖抽象时间源，生产环境由系统时间实现，测试使用可控假时间。模块不得直接调用系统时钟。

离线结算遵循：

1. 读取上次可信保存时间和当前时间。
2. 负时长按零处理并记录时钟回拨。
3. 对间隔应用已确认的离线收益上限。
4. 使用纯函数按区间计算收益，不逐秒模拟。
5. 一次性提交状态并保存，确保重复启动不会重复领取。

本地单机无法彻底防止改时间作弊。MVP 只做异常检测、上限和存档完整性保护；若未来引入排行榜，时间与关键进度必须改由服务端裁决。
