# 设计游戏功能

## 输入

- 用户目标与期望体验。
- 现有 MVP、ADR、相关代码和数据定义。
- 平台、存档、更新及美术约束。

信息不足且不同答案会改变架构时，每轮只询问 1–2 个关键产品问题；可采用安全默认值的问题直接给出推荐。

## 流程

1. 先按 `.cursor/skills/research-idle-market/SKILL.md` 核对 `docs/research/` 里最新市场对照；没有或过期则先补调研，禁止凭记忆定玩法。
2. 阅读 `docs/product/mvp-scope.md` 和相关 ADR，判断需求是否超出当前里程碑。
3. 用玩家可观察行为写出验收标准，包括首次进入、重复操作、离线恢复和失败路径。
4. 定义状态、输入、输出、数值来源及不变量；标明哪些数据需要存档或远程配置。
5. 划分领域规则、功能用例、UI/场景和平台接口，保持单向依赖。
6. 分析对存档 schema、内容版本、性能、素材、测试和旧版本兼容的影响。
7. 给出最小垂直切片，列出明确不做的内容，避免一次引入多个核心循环。
8. 若涉及重要且长期的取舍，先新增 ADR；否则将方案写入对应设计文档。

## 输出

- 目标与非目标。
- 玩家流程和验收标准。
- 状态/数据模型及边界条件。
- 文件与模块变更范围。
- 测试策略、迁移需求、风险和待确认决策。

设计完成不代表允许扩大范围；实施必须遵循项目 Rules 和已确认边界。
