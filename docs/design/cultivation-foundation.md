# 放置修仙基础逻辑

本文只整理**修为轴底座**。历练轴见 `docs/design/adventure-loop.md` 与 ADR-0003。`0.1.2` 已按此底座实现第一个可玩版本。`0.1.4` 补了界面反馈。`0.1.6` 在同一时间入口上并联历练结算，不改本页修为公式。

数值表是示意曲线，用来看形状和模块边界，不是正式投放数值。

## 目标与非目标

目标：玩家打开游戏就能感到“时间在帮我变强”，并反复完成同一条闭环。

玩家可观察的闭环：

`时间流逝 → 修为增加 → 修为足够 → 突破境界 → 修炼变快 → 下次突破更远`

非目标：

- 第二套玩法循环。
- 账号、云存档、排行榜、管理后台、业务服务器。
- 正式美术与完整境界世界观文案。
- 把特色系统提前做进底座。

## 玩家流程

1. 首次进入：境界为凡人，修为为 0，按配置显示当前修炼效率，并创建本地存档。
2. 在线停留：修为按效率持续增加，进度条指向下一次突破。
3. 修为达到消耗：突破可点。
4. 突破成功：扣除消耗、境界前进一阶、效率提高、立刻存档。
5. 退出再进入：按统一时间入口结算离线收益，只发一次，再继续在线增长。
6. 已到当前配置最后一阶：仍可获得修为，不再出现下一阶突破。

## 验收标准

- 首次进入后能看到境界名、当前修为、每秒效率和下一阶消耗。
- 等待数秒，修为数字上升，且与效率一致。
- 修为不足时不能突破；足够时突破后境界、效率和消耗同时变化。
- 杀掉进程再打开，进度还在；不会无故变成新号。
- 离线一段时间再打开，修为一次性增加，刷新界面不会再发同一段离线收益。
- 把设备时间往回调，修为不减少、不倒算。
- 离线超过上限时，只按上限结算，并让玩家知道“只计算了 N 小时”。

## 数值策划：先定公式，后填表

底座只承认三条公式。具体数字进配置表，不写死在界面或突破按钮里。

在线与离线共用：

```text
本段获得修为 = 当前效率 × 经过秒数
```

突破：

```text
若 当前修为 ≥ 当前突破消耗 且 存在下一境界：
    修为 -= 突破消耗
    境界 = 下一境界
```

境界表的生成形状：

```text
效率(n) = G0 × g^n
消耗(n) = C0 × c^n
纯在线突破时间(n) = 消耗(n) / 效率(n) = (C0 / G0) × (c / g)^n
```

只要 `c > g`，每一阶都会更慢。这是放置游戏能“越玩越长、又越来越强”的最低条件。

公式形状仍按上面理解；数字是手调，不是 `G0=1` 那张表。离线上限 8 小时。正式投放仍以 `game/resources/config/idle_rules.json` 为准。

| n | 境界 | 效率（修为/秒） | 突破消耗 | 纯在线突破 |
| --- | --- | ---: | ---: | --- |
| 0 | 凡人 | 2.0 | 360 | 约 3 分钟 |
| 1 | 炼气初期 | 3.5 | 1260 | 约 6 分钟 |
| 2 | 炼气中期 | 6.0 | 2880 | 约 8 分钟 |
| 3 | 炼气后期 | 10.0 | 4800 | 约 8 分钟 |
| 4 | 炼气圆满 | 18.0 | 16200 | 约 15 分钟 |
| 5 | 筑基初期 | 35.0 | 42000 | 约 20 分钟 |
| 6 | 筑基中期 | 70.0 | 120000 | 约 29 分钟 |
| 7 | 筑基后期 | 140.0 | 800000 | 约 1.6 小时 |
| 8 | 金丹初期 | 220.0 | 4000000 | 约 5.1 小时 |
| 9 | 金丹中期 | 360.0 | 18000000 | 约 13.9 小时 |
| 10 | 金丹后期 | 560.0 | 80000000 | 约 39.7 小时 |

前三阶合计约 17 分钟，用来撑起第一次回来整理，而不是打开就能连点完。20–30 分钟会话应还能突破，同时下一关仍可能卡住。更后面的阶用来验证离线上限和只结算一次。

突破规则的底座选择：

- 消耗从修为里扣除，**剩下的修为保留**。
- 满足消耗即成功，**不引入失败概率**。失败、心魔、丹药是后续特色。
- 不在突破时把修为清零。清零属于飞升/重置，是第二条循环。

## 状态与数据边界

配置（可随内容包更新，不进玩家存档）：

```text
RealmDef
  id
  display_name
  order
  gain_per_second        > 0
  breakthrough_cost      > 0
  next_id                空表示当前最后一阶

IdleRules
  schema_version
  offline_cap_seconds    > 0
```

玩家存档（只存算不出来的状态）：

```text
payload
  cultivation            ≥ 0
  realm_id               必须能在配置里找到
  last_settled_unix      上次成功结算的 Unix 时间
```

外层信封继续使用已有存档设计：`schema_version`、`app_version`、`content_version`、`saved_at_unix`、`checksum`。

不存档：

- 每秒效率、下一阶消耗、进度百分比（都能从境界表算出来）。
- 按钮高亮、弹窗、滚动位置。

时间：所有模块只问 `TimeService`。禁止直接读系统时钟。离线结算是纯函数：同一段时间、同一个效率，结果必须相同。

## 不变量

- 修为永不为负。
- `realm_id` 永远指向当前配置里存在的境界。
- 经过时长小于 0 时按 0 处理，并记录时钟回拨。
- 结算后必须写下新的 `last_settled_unix`，同一段离线不能领两次。
- 突破失败（不足或已到顶）不得改境界，也不得扣成负数。
- 配置缺失、消耗或效率小于等于 0 时拒绝加载，不能静默用错表。

## 必须搭建的模块

| 模块 | 职责 | 不该做的事 |
| --- | --- | --- |
| `TimeService` | 给出“现在”和两段时间的间隔 | 计算修为 |
| `ConfigService` | 加载并校验境界表与离线上限 | 改玩家进度 |
| `Cultivation` 领域规则 | 按时长加修为、判断可否突破、执行突破 | 读文件、读时钟、画 UI |
| `SaveService` | 临时文件 → 校验 → 原子替换，保留备份 | 懂境界公式 |
| 主界面 | 显示境界、修为、效率、进度、突破按钮 | 自己保存一份数值表 |

依赖只能朝领域规则走：界面调用用例，用例调用纯规则，适配层负责存档和时间。

## 最小垂直切片

一次做通，不再并行开第二条玩法：

1. 境界配置表与校验。
2. 修为随时间增加。
3. 突破与效率变化。
4. 本地存档读写。
5. 离线结算与上限。
6. 一张竖屏主界面。

明确不做：自动突破、多种货币、经验条以外的资源、随机失败、飞升重置、任务、商店。

## 对现有工程的影响

- 存档：新增 `payload.cultivation`、`payload.realm_id`、`payload.last_settled_unix`，`schema_version` 从 1 起步。
- 内容：新增 `game/resources/config/` 下的境界表，后续可用内容包替换数字，不必改程序。
- 更新：第一段闭环仍走现有 APK 更新；不在本切片实现内容包热更。
- 测试：公式、突破边界、离线上限、时钟回拨、坏档恢复必须有 GUT 单测。
- 素材：继续占位，不阻塞逻辑。

## 风险

- 正式数值以后会改很多遍。所以数字必须进表，测试要按“读表后的公式”写，不能写死今天的示意数字。
- 本地单机改时间无法彻底防。底座只做回拨检测和离线上限；排行榜出现之前不要为此上服务器。
- 大数显示（万、亿）第五阶之后就会碰到，属于界面规则，不进入领域公式。

## 待确认决策

下面两项不影响“要不要先搭底座”，实施第一刀时按推荐值即可：

1. 在线刷新：推荐每秒结算一次并刷新数字，不逐帧补算。
2. 离线上限：推荐先用 8 小时，后续只改配置。
