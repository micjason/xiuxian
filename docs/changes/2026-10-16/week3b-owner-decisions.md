## 做了什么
1. **推荐战力后台手填**：`content_stages.recommended_power`（迁移 0021，默认写入 lianqi_3=900、zhuji_3=2450、jindan_3=6590，只在没填时写）。0 = 没填，退回"首领战力 × 推荐战力系数 1.05"。`/content/current` 不再覆盖手填值（原 `content/routes.ts:61` 的覆盖已去掉）。后台关卡表单加"推荐战力"输入框、列表列显示有效值（没填时标"自动"）、自动算出值作参考；客户端关卡页/战斗页显示下发值。
2. **掉落**：模拟脚本加了每次结算的击杀数/阵亡/掉落指标（`metrics.waves`）。结论：击杀数低于设计表（实测 655 只/小时 vs 表 764–875），每击杀掉率 4.04% 与配置一致 → **没有调到 5%**。详见 `sim_report_week3b.md` §1。
3. 九层通关时间不动（A 2.60 天 / B 4.25 天含 0.25 天起步等待）。
4. **突破石 +50%**：首领重复挑战的下品石概率 35%→52.5%、中品 15%→22.5%（`prototype-v12.ts` 种子 + 迁移 0021 只改还是旧默认值的；后台首领编辑器可调）。模拟复跑：B 日程 5.29 天内突破 5→13 次，但**没有走完全部突破**；要全部走完需要约旧值 3 倍，数据见报告 §2，等负责人定数。
5. **满包不再拒绝挑战首领**：服务器删掉 BAG_FULL 拒绝和"开战前腾格"；容量只管装备；装备在满包时不掉（自动分解开着：白/绿直接分解成强化经验，蓝/紫腾一件未强化白/绿，腾不出就不掉）；首通固定奖励可以超容量；突破石、功法书（材料）不受容量限制。结果返回 `bagFull: true`。客户端：开战前背包满时战报里一行提示；结果页有"背包已满，装备没有掉落"；弹窗「背包已满（20/20）／新掉落的装备没能入包，请先分解装备」，带「去背包」。
6. 客户端与设计稿的已知差异（剪影占位、12 s 心跳、自动战斗只显示状态）按负责人决定在原型阶段接受，没有改。
