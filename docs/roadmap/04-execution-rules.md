# 04 执行规范（给执行代理）

每个任务开始前读一遍本文件。本文件与 `.cursor/rules/` 冲突时，以本文件为准，并在任务汇报中指出冲突。

## 1. 一个任务的标准流程

1. **读规格。** 读 `03-dev-plan.md` 中该任务的全部内容，以及 `02-target-architecture.md` 中它引用的章节。规格不清楚或互相矛盾时，按“更保守、更不破坏数据”的方式理解，并在汇报的“待确认”里写明，不要自行扩大范围。
2. **建分支。** 从最新 `dev` 拉分支，命名 `task/<任务编号>-<简短英文>`，例如 `task/P1-1-transactions`。
3. **先写测试。** 后端纯规则和 service 先写失败的测试，再写实现。修缺陷时先写能复现缺陷的测试。
4. **实现。** 只改任务列出的范围。发现范围外的问题，记到汇报的“发现的其他问题”里，不要顺手改。
5. **自检。** 运行第 3 节的检查命令，全部通过。
6. **提交。** 按第 2 节的提交规范，小步提交。
7. **汇报。** 按第 5 节格式汇报。
8. **合并。** 推送分支并开 PR 到 `dev`，CI 通过后合并（项目负责人可以要求先审再合）。

## 2. 提交规范

- 格式：`<type>(<scope>): <中文或英文描述>`，type 用 `feat`、`fix`、`refactor`、`test`、`docs`、`chore`；scope 用 `backend`、`admin`、`game`、`docs`、`ci`、`deploy`。
- 一个提交只做一件事。单个提交原则上不超过 400 行改动（自动生成的迁移文件、锁文件除外）。
- 后端、后台、客户端的改动分开提交。
- 禁止提交：`.env`、密钥、签名文件、`node_modules/`、`dist/`、构建产物、数据库备份、`.DS_Store`。

## 3. 检查命令（宣称完成前必须实际运行并贴出结果）

| 改动范围 | 必跑命令 |
|---|---|
| `backend/` | `npm run typecheck`、`npm run lint`、`npm test`（需本机 `docker compose up -d`） |
| `backend/src/db/schema.ts` | 额外：`npm run db:generate` 后再运行一次确认不再产生新文件；在空的测试库上 `npm run db:migrate` |
| `admin/` | `npx vue-tsc --noEmit`、`npm run lint`、`npm run build` |
| `game/` | Godot 无头导入与 GUT：参见 `.cursor/skills/verify-godot-project/SKILL.md`；界面改动额外在 1080×1920 窗口截图 |
| 文档 | 检查链接路径存在 |

没有实际运行的检查，汇报里不得写“通过”。

## 4. 硬性禁止

- 禁止在未备份的情况下对测试服或正式服数据库执行任何删除、重建、迁移。
- 禁止修改已经执行过的迁移文件；禁止手写迁移 SQL。
- 禁止在任何玩家接口中采用客户端传来的修为、境界、属性、掉落、成功率等数值。
- 禁止在客户端新增任何结算、随机掉落、战斗胜负判定、本地进度存档代码。
- 禁止在主线程用循环等待网络（`while` + `OS.delay_msec`）。
- 禁止在代码中写死服务器 IP、域名、密码、令牌。
- 禁止把 GM 接口暴露在 `ENABLE_GM_TOOLS` 关闭的环境。
- 禁止修改或删除 Android 签名文件、证书、`/Volumes/kaixia/GodotDev` 下的工具链。
- 禁止一次性提交跨多个任务的大改动。
- 禁止为了让测试通过而删除或放宽测试断言。确实需要改测试时，在汇报中说明原因。

## 5. 汇报格式

```markdown
## 任务 <编号>：<名称>

### 完成内容
- 用一两句话说明做了什么、玩家或管理员能看到什么变化。

### 改动文件
- path/to/file — 改了什么

### 验证
- 运行的命令和结果（通过/失败数量）
- 手工验证步骤和结果（界面任务附截图路径）

### 验收标准逐条核对
- [x] 标准 1 ……
- [ ] 标准 2 ……（未满足的说明原因）

### 发现的其他问题
- 范围外发现的问题，未处理

### 待确认
- 规格不清、需要项目负责人决定的点
```

## 6. 编码约定

### 后端

- 目录：`src/modules/<业务>/` 下分 `rules.ts`（纯函数）、`service.ts`（数据库操作，第一个参数是 `Tx`）、`routes.ts`（只做 schema、鉴权、调用 service、返回）、`*.test.ts`。
- 时间和随机数通过依赖注入（`deps.now()`、`deps.randomInt()`），规则函数不直接调用 `Date.now()` 或 `Math.random()`。
- 服务端随机统一用 `crypto.randomInt`，不用 `Math.random`。
- 数据库查询禁止在循环里逐条查询（N+1），列表一律分页。
- 错误一律抛 `AppError`，不返回字符串原因。

### 后台

- 每类内容一个表单组件；引用字段一律用 `SlugSelect`；不在页面中手写 `fetch`，统一用 `api.ts`。
- 所有用户可见文案用中文。

### 客户端

- 强类型 GDScript；每个页面一个场景 + 一个脚本，脚本不超过 400 行。
- 页面只读 `GameStore`、`ContentCache`，操作只通过 `ApiClient`；页面之间不直接调用。
- 名称、描述一律从内容快照读取，不写死在脚本里。

## 7. 遇到阻塞时

- 外部条件不满足（例如域名未备案、服务器无法登录、需要密钥）：完成能完成的准备工作（配置文件、脚本、文档），在汇报的“待确认”中写清楚缺什么，然后继续下一个不依赖它的任务。
- 规格本身有错误（例如公式算出不合理的结果）：不要自行改公式；在汇报中给出具体数字和建议的修改，等项目负责人确认。
