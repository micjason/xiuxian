## 0. 怎么使用这份清单

1. 先读第 1 节产品快照和第 2 节「已完成盘点」，避免把已落地系统再做一遍。
2. 第 3 节竞品对照只提供结构借鉴，禁止复制竞品名称、文案、数值、美术或代码。
3. 第 4–7 节按阶段列出**尚未完成或仅部分完成**的任务。已完成项不进入任务表。
4. 每条任务都按同一模板书写，可直接拆成开发单。实现前仍须写出可观察验收标准，并按仓库质量门禁验证（`.cursor/rules/quality-gates.mdc`）：改 `backend/` 或 `admin/` 跑该目录检查；改 Godot 至少无头导入与相关 GUT；高风险结算与迁移必须覆盖失败路径。
5. 遇到第 9 节「未决事项 / 非目标」，不得自行当作已批准范围。需要产品负责人书面确认后再开工。
6. 权威规则在服务器。客户端只展示和发起请求。不要把新的进度规则写回手机本地结算。
7. 开发阶段不少后台配置是「保存即生效」。战斗预览页是明确例外：只写隔离草稿，不得发布到游戏。

## 1. 产品快照（以仓库事实为准）

《修仙》是 Android 优先、竖屏（画布 1080×2340）的放置修仙游戏。技术组成：

| 端 | 路径 | 技术 | 当前角色 |
|---|---|---|---|
| 客户端 | `game/` | Godot 4.7.2，强类型 GDScript | 展示与操作；登录后经 `PlayerApi` 访问本机或指定服务器 |
| 后端 | `backend/` | TypeScript + Fastify + PostgreSQL（Drizzle） | 权威结算、内容、战斗时间轴、洞府与迷雾 |
| 后台 | `admin/` | Vue 3 | 配表、体检、模拟、公告、安装包、战斗预览草稿 |
| 工具 | `tools/` | 本机启动、模拟、Android 发布脚本 | 本机开发与测试包流水线 |

产品层次仍以 ADR-0005 为准，但若干后续 ADR 已修正细节：

- **修为轴**：时间产修为 → 突破提升境界与效率。突破有概率，受战力影响并带保底（ADR-0007，已取代「突破必成」）。
- **历练轴**：选关挂机战斗、掉落入行囊、穿装备、学功法、打首领过墙。
- **洞府经营**：把时间和材料转成草药、丹药、定向装备，反哺前两轴。洞府已在后续里程碑落地，不再处于 ADR-0007「第一版不上线」的暂停状态。
- **传承元循环**：仍是长线设计目标，仓库中**尚未实现**。

当前客户端工程版本是 `0.18.30`，`versionCode = 70`，包名 `com.micjason.xiuxian`（见 `game/project.godot`）。默认接口地址是 `http://127.0.0.1:8080`。根目录 `README.md` 仍写「已发布客户端 0.6.7 / versionCode 24」，**已过时，不得当作当前进度**。

信息架构（已实现）：底栏五格为「修炼 / 历练 /【突破】/ 洞府 / 背包」。功法是修炼页的子入口，不占底栏；迷雾从洞府进入；首领战从历练进入。顶栏有头像（进设置）、境界、战力、灵石、修为条。葫芦货币和邮件按设计稿展示，点击提示「功能暂未开放」。

## 2. 已完成进度盘点（不要再做成「剩余任务」）

以下系统在 `dev@4a14f53` 上已经可玩或可配置。细节仍可能要修，但主链路不是从零开始。

### 2.1 账号与服务器权威循环

- 玩家注册 / 登录 / 登出：`POST /auth/register`、`/auth/login`、`/auth/logout`；客户端 `game/scripts/ui/player_login.gd`，登录页可填服务器地址并写入本机。
- 打开游戏由服务器结算：`GET /me`、`GET /me/state`；写操作带幂等键。
- 离线结算与离线战报确认：`player_offline_reports`、`POST /me/offline-reports/:id/ack`，离线上限配置为 8 小时（28800 秒，亦见于历史 `idle_rules.json`，正式数字以服务器 `content_globals` / tuning 为准）。
- 前台心跳定时拉状态，切后台暂停、回前台补拉（`play_screen.gd`）。
- 过期存档防护、公告 / 弹窗队列、安装包更新检查与系统安装器覆盖安装流程已存在。

### 2.2 修为、境界、突破

- 出厂境界为固定 8 大境界 × 3 层，共 24 层：炼气 → 筑基 → 金丹 → 元婴 → 化神 → 炼虚 → 合体 → 大乘（`backend/src/modules/content/realm-factory.ts`）。后台「境界」页只调修为、属性和突破关卡，名称不可随意改成另一套梯子。
- 出厂突破关卡闸目前挂在炼气 / 筑基 / 金丹共 9 层同名关（`lianqi_1`…`jindan_3`）。元婴及以后出厂不挂闸，避免表没配完时卡死。
- 突破弹窗、条件不足可点进关、成功演出已接通。突破走 `POST /me/breakthrough`。

### 2.3 历练、战斗、掉落

- 原型内容：8 章 / 24 关，每关有首领；普通怪与首领掉落可配；橙装只从首领重复奖励的橙色档出。
- 挂机选关、离线同步结算历练掉落、自动分解（按品质勾选，默认白绿蓝）已完成。
- 首领挑战走持久战斗日志：`POST /me/combat/start`、`GET /me/combat/pending`、`POST /me/combat/:id/finish`（complete / skip / retreat）、`POST /me/combat/:id/ack`。断线不丢胜负；只有明确撤退会在结算前记为失败。大招已改为全自动。
- 客户端用统一时间轴 `TimelineBattlePage` 同时承接历练与迷雾；倍速 ×1/×2/×3；可在规则允许时跳过已获胜战斗。
- 战斗公式、战力权重、试炼人偶、进度模拟（后台「进度模拟」）已有。

### 2.4 行囊、装备、强化、功法

- 六部位（武器、头、身、手、腿/鞋、饰品）；公式装备与手动装备、套装；行囊初始 20 格，容量字段保留。
- 分解得炼器精粹、部位强化（强化绑格子，换下归零）、品质突破节点、已穿戴不可分解。
- 功法学习、运转 / 停止、技能层数与栏位、默认功法与换装外观档位、九套技能特效模板已接通。
- 物品详情弹窗、批量分解、挂机掉落飞入背包反馈已有。

### 2.5 洞府

已形成可玩闭环，不是空页面。服务器接口在 `backend/src/modules/dongfu/routes.ts`，客户端 `cave_page.gd`：

### 2.7 后台与内容管线

已有完整配置信息架构（`admin/src/nav.ts`）：配置概览、境界、物品、装备、技能、章节、关卡与 Boss、掉落表、强化、战斗公式、洞府、进度模拟；发布与体检、版本历史、客户端安装包；公告与弹窗；玩家管理（含清空进度、装备发放）；操作日志；单管理员。

### 2.9 必须诚实写出的缺口（已有系统上的缺口，不是「完全没做」）

- **官方战斗攻击序列帧并未交付，也已被放弃作为「已有合格素材」。** 当前实战表现依赖：用户提供的动作表切片（人物源图约 130px，放大偏软，商用许可未独立核验）、熊王静图 + 代码补动作、既有 Q 版技能特效与关节网格兜底。不要把现有帧写成「正式合格的一整套攻击动画」。

## 3. 竞品与类型差距（仅公开可核信息）

对照目的：找出本游戏「已有骨架但不够厚」或「类型常见但我们明确未做」的系统。借鉴结构，不抄内容。旧调研见 `docs/research/`（2026-09-10 / 09-11），其中「不要做服务器」的产品结论已被 ADR-0006 取代，结构观察仍有效。本次于 2026-11-23 复核公开页，并补了若干可核来源。

### 3.1 一念逍遥（头部商业放置修仙）

可核来源：Google Play 简介、官方网站神通攻略、官方/论坛关于洞府与宗门的说明、主策划/发行采访（仓库调研 L3/L4）、玩家攻略中可观察到的系统清单。

公开可见结构：

- 强调「离线仍在世界里真实战斗和产出」，是服务器常驻对象，不是「上线按公式补一次」。
- 养成线多：修为、功法（激活 / 圆满）、古宝、法宝、仙友、洞府灵气、丹药炼器、药园。
- 修炼方向（体 / 法 / 剑 / 鬼 / 儒 / 血等）影响神通与法宝搭配。
- 城镇式系统入口：宗门、镇妖塔、论剑、坊市、排行、悬赏、拍卖、异界等。
- 宗门提供俸禄、建设、事务、除魔、灵脉、藏经阁兑换；社交与跨服是长线支柱。
- 长线问题在公开评论和策划复盘中反复出现：日清短、后期重复；同时有相当比例玩家可以不深度参与社交。

对《修仙》的含义：

- **不要**把「服务器真挂机 / 宗门乱斗 / 跨服 / 多养成线并行」当成当前必须实现的范围。ADR-0006 允许以后加社交，但第一优先级仍是单人闭环深度。
- **可以借鉴的结构**：回访要有「今天能做完的事」；功法或经营选择要能改主循环效率；大境界才换体验，小层保持同一套界面。
- 我们已有「上线按服务器时间补一次」的离线模型，与竞品「世界持续模拟」不同，这是已定方案，不是缺陷。

### 3.2 寻道大千（商业放置养成）

可核来源：37 官网「玩法介绍」、2026-10 官方/渠道更新说明（丹界、周天星象等）、TapTap 攻略分区。

公开可见结构：装备（砍树 / 仙树 / 渡劫解锁品质）、座驾、灵兽（上阵、吞噬升星、羁绊）、精怪、血脉；后又叠加丹界种植炼丹、星象养成、妖盟竞赛等。流派（闪避、连击、击晕、回血、反击等）是长期内容深度的主要来源。更新频率高，系统持续叠加。

对《修仙》的含义：

- 竞品用「多套可点的平行养成」撑寿命；我们的已决架构是双轴 + 洞府供给，而不是再开灵兽 / 星象 / 座驾。
- 可借鉴的是：**已有系统的目录要厚**（更多种子、配方、图纸、关卡事件、功法选择），以及「材料有明确去向」。不要为了看起来像商业作而增加第六底栏或孤立小游戏（ADR-0005）。
- 丹界类「种植 → 炼丹 → 服丹加属性 / 订单消耗过剩产出」与我们已有药园 / 炼丹相近，优先加厚现有洞府，而不是另做一套家园。

### 3.3 「无名修仙录」及名称相近作品

本次未能核到 TapTap / 官方商店上恰好名为「无名修仙录」的稳定官方页。检索到的多是第三方下载站泛化介绍，或名称相近但并非同一产品的页面，例如：

- 《修仙录》（文字回合制，开发者自列洞府修炼、境界、装备功法、秘境、签到、商店、日常 / 主线任务、邮件、兑换码等）
- 《挂机放置修仙录》（2026-10 抢先体验，五人小队肉鸽刷宝，买断制单机，与本项目品类不同）
- 《混沌修仙录》等测试页

**因此本文不把第三方下载站里的功能清单当作「无名修仙录」的已核特性。** 若负责人指定的对照对象是其中某一款，请提供官方商店或官方介绍链接后再补差距。就「竖屏放置修仙」这个类型而言，可从已核的极简作 / 文字作中归纳常见结构：离线修为、境界突破、关卡 / 秘境、功法装备、洞府炼丹、签到与日常任务。后两项在本项目 A 阶段被有意推迟。

### 3.4 国际放置结构（只取机制，不取主题）

可核来源：Melvor Idle 官方 wiki（Tutorial、Offline Progression、Township Tasks）、通用 idle 设计论述（仓库调研 S10/S11）。

- 新手引导是「做一件能立刻改变下一动作的事」（挖矿 → 锻造 → 装备 → 战斗），而不是长篇说明书。
- 离线有明确上限（Melvor 为 24 小时），回来给摘要，在线与离线同一套规则。
- 时长来自「技能 × 物品精通」的目录厚度，而不是不断加互不相干的按钮。
- 回访可用循环任务，但 Melvor 的 Township casual tasks 是 5 小时刷新，不是强耦合的「每天清体力」。
- 行业常见离线封顶 4–24 小时；重置 / 飞升是撞墙之后的第二圈，不是开局内容。

## 4. 第一阶段：基础巩固与可玩闭环补齐

目标：一个外部开发者按文档在本机拉起 `dev`，从注册到挂机、突破、打关、穿装、强化、洞府、迷雾，不靠改库能走通；新手不被扔在空白主界面上；文档与代码不再互相打架；战斗表现的真实缺口被说清楚而不是被假装已经完成。

### FND-03 首局引导（注册后的 3–10 分钟）

- **状态**：缺失（炼气首关有教学向数值：精英手填、关掉自动挑战；但没有引导流程、高亮或任务）
- **玩家目标**：第一次进入游戏，不用问人就知道「看修为涨 → 去历练打第一关 → 穿装备 / 分解 → 条件够了再突破」，并知道洞府和迷雾要稍后才会用到。
- **做法**：
  - 不要做长篇剧情或强制失败。做 4–6 步可跳过的弱引导，数据可由后台「新手设置」或新的 `content_globals.newbieGuide` 配置。
  - 建议步骤：① 主界面看到修为条在涨；② 打开历练，挑战 `lianqi_1`（已是教学关）；③ 战斗结束后打开战报与掉落；④ 到背包穿上或分解；⑤ 修为或关卡条件满足时引导点底栏突破；⑥ 提示洞府入口存在，但不强制完成种植。

- **主路径**：client、backend、admin
- **验收**：新号从注册到第一次突破（或明确看到「还差多少 / 需击败首领」）不需要口头讲解；跳过与已完成标记在重登后保持；引导不修改战斗结果。
- **依赖**：无（可并行于文档清理）
- **优先级**：P0
- **风险**：不要做成无法关闭的遮罩。首关数值已单独调过，引导不要再改伤害公式。

### FND-04 离线收益说明与封顶体验

- **状态**：部分完成（结算和弹窗已有，上限与构成对玩家未必足够清楚）
- **玩家目标**：离开再回来时，能看懂这段时间拿了什么、为什么不再涨、该去强化还是去领取洞府。

### FND-05 满包、扩容来源与失败防线

- **状态**：部分完成（20 格、满包提示、自动分解已有；扩容道具「以后由活动或任务发放」，当前没有获取途径）

- **风险**：禁止使用竞品地名或受保护的角色名。

### CNT-03 成长曲线与掉落再平衡（正式可玩，而不是示意表）

- **状态**：部分完成（有数值方案、模拟器、多次掉率调整；文档仍多次提到示意 / 草稿首领）
- **玩家目标**：正常游玩节奏接近出厂 eta（炼气一层约 30 分，到大乘三层约 55 天量级），不会第一天突破失控，也不会在某一层永久卡死。
- **做法**：以 `tools/sim`、`backend/src/modules/sim/progression.ts`、后台进度模拟为工具，固定「标准角色」与目标时长，按 ADR-0008 回写首领。检查金丹三层等历史「原型 0 消耗」是否仍残存在某份种子里（出厂表本身已有消耗，需核对已发布库与种子一致性）。产出报告：每层期望天数、卡死点、橙紫掉率、强化材料是否跟得上闸门。
- **主路径**：backend、admin、docs
- **验收**：模拟报告附在变更记录；至少覆盖到金丹三的卡死项为 0，或每条卡死有策划解释；不改公式前提下调表可复现。
- **依赖**：无
- **优先级**：P1
- **风险**：改掉率会影响已有测试号；只在本机库试验，不要默认去动共享或正式库。

### CNT-04 洞府目录加厚（种子、配方、图纸）

- **状态**：部分完成（设施闭环已有，目录偏薄，长线设计要求「一周内点不完」）
- **玩家目标**：药园、炼丹、炼器在前七天始终有「下一个可种 / 可炼 / 可造」，产出能用于突破、战斗或强化。
- **做法**：在后台洞府页扩充种子与成熟时间、配方（修为向、战斗临时向、经营向）、炼器图纸（定向槽位胚，不做无限随机重铸）。保证每类重复产出至少两个去向。主线必需材料要有确定来源或累计保底。不在 v1 上做炼丹爆炉、付费加速。
- **主路径**：admin、backend、client
- **验收**：新号按正常节奏，7 日内可见不少于一套完整的「种 → 炼 → 使用见效」和一套「材料 → 炼器 → 装备变化」；配置可在后台增删而不改客户端代码。
- **依赖**：CNT-03 的材料供需账
- **优先级**：P1
- **风险**：资源家族不要一次加太多，避免认知负担（ADR-0005）。

### CNT-05 藏经阁（功法研修设施）

- **状态**：缺失（ADR-0005 / 长线设计已规定，洞府 v1 明确不做，现在应当作为下一设施）
- **玩家目标**：重复功法残页和研修时间可以定向补已见功法，而不是只能堆在背包。
- **做法**：按 ADR-0005：消耗残页与时间，补已见功法参悟或解锁构筑知识；**不能凭空生成尚未见过的高阶功法**。入口放在洞府，不新增底栏。数据：设施等级、研修队列、残页物品、与 `player_skills` 的进度字段。结算纳入统一时间，预扣投入，离线到时领取。后台可配队列长度与消耗。客户端洞府总览增加设施卡，完成态与红点与药园一致。
- **主路径**：backend、client、admin
- **验收**：未见过的功法无法被研修出来；已见残页可转化为等级 / 进度；取消队列返还规则明确；离线与在线同一套时间。
- **依赖**：CNT-04（残页来源要先稳）
- **优先级**：P1
- **风险**：不要做成第二套技能树界面。功法页目前是子页，藏经阁在洞府，两边文案要一致。

### CNT-06 功法构筑可见化与默认搭配

- **状态**：部分完成（运转 / 停止、栏位、默认功法已有，玩家缺少「为什么要换这本」的反馈）
- **玩家目标**：能看出功法如何改修炼效率或战斗数，并在已有书里做选择，而不是只点升级。
- **做法**：功法页展示每本对修为速率、攻击、冷却、特效类型的差量；提供 2–3 个官方推荐搭配（可来自 `outfit-skill-defaults` 的扩展），玩家可一键装备但仍可手改。不要做付费抽技能。
- **主路径**：client、admin
- **验收**：更换运转功法后，主界面速率或战力分解立即变化；推荐搭配不覆盖玩家未确认的选择。
- **依赖**：无
- **优先级**：P2
- **风险**：战力分解已有 `power-explain`，优先复用，不要另做一套公式。

### CNT-07 迷雾第二图与地图配置化

- **状态**：部分完成（问心谷闭环 + 自动走路已有，`DEFAULT_FOG.maps` 只有一张）
- **玩家目标**：洞府里的秘境不是一次性景点；第二张图有新障碍、事件和奖励，并仍走同一套移动 / 战斗规则。
- **做法**：把地图从代码默认值进一步收到可在后台编辑的 `globals.fog`（已有解析与兼容逻辑）。先做一张与问心谷同等规模或略大的第二图，解锁条件用境界或问心谷探索完成度。事件选项继续是轻量分歧（战斗 / 离开），不要做成完整任务岛。旅行点日限额与揭示半径保持可配。
- **主路径**：backend、admin、client、art
- **验收**：两张图可切换；旧档问心谷进度不丢；自动走路在新图障碍上仍然正确；战斗与掉落走权威接口。
- **依赖**：ART-03 的占位即可先上
- **优先级**：P1
- **风险**：`travelPointsMax` 有过历史兼容（旧值 20 会被纠正为 200），改默认值要写迁移或兼容说明。

### CNT-08 迷雾物件与事件库

- **状态**：部分完成（问心谷含 3 怪、3 箱、1 事件）
- **玩家目标**：探索有「再开一次说不定遇到不同选择」的轻度变化，但不靠纯随机卡死必过内容。
- **做法**：扩展事件模板（战斗、奖励、加临时 buff、给种子 / 残页）。必过出口与关键宝箱保持确定；随机只影响额外奖励。后台最好能按地图编辑物件，而不是只改代码常量。
- **主路径**：backend、admin、client
- **验收**：同一张图的关键路径可 100% 完成；随机事件有种子或可复现测试；选项文案可配。
- **依赖**：CNT-07
- **优先级**：P2
- **风险**：不要引入「理智清零丢光本局」这类重惩罚（非本产品已决体验）。

### CNT-09 装备套装与定向获取

- **状态**：部分完成（套装配置与后台抽屉已有，玩家侧的「收集一套」目标可能不够显眼）
- **玩家目标**：知道某些部位凑齐有套装效果，并知道应从哪一章或哪次炼器获得。
- **做法**：在装备详情和背包筛选中展示套装进度与效果。保证每套至少有一条非纯随机来源（指定掉落、炼器图纸或里程碑）。法宝 / 灵宠格子继续预留，本阶段不开放（见 OPEN-03）。
- **主路径**：client、admin、backend
- **验收**：集齐效果在战力分解中可见；缺少部件时有获取说明；不开放的格子若显示则用「暂未开放」，不给假数据。
- **依赖**：CNT-02、CNT-04
- **优先级**：P2
- **风险**：不要做无限随机重铸（已禁止）。

### CNT-10 临时丹药与战斗 / 修炼的可见反馈

- **状态**：部分完成（`player_active_buffs` 与洞府炼丹已有）
- **玩家目标**：吃药后能在战报、属性或修为速率上看到「还剩多久」。
- **做法**：主界面或角色详情显示进行中的 buff；过期后消失；战斗结算使用服务器时间，不在客户端自行延长。检查多种丹药叠加规则（同类型刷新还是拒绝），写入后台说明。
- **主路径**：client、backend
- **验收**：使用攻击临时丹后再打关，战报或预览属性有变化；到期后恢复；离线期间计时不作弊。
- **依赖**：CNT-04
- **优先级**：P2
- **风险**：避免变成必须吃满药才能过主线；主线关卡应在不吃稀有丹时也可过。

### CNT-11 灵石经济（获取与消耗，不含充值）

- **状态**：部分完成（顶栏展示 `spiritStones`，洞府升级 / 某些兑换可能消耗；顶栏「+」锁着「暂未开放」）
- **玩家目标**：灵石是经营与配方的通用费用，但不能单独替代关键素材（ADR-0005）。玩家知道它从哪来、花到哪去。
- **做法**：盘点所有加减灵石的接口，做一张来源 / 消耗表。保证前期有不付费来源（关卡、洞府、里程碑）。「+」按钮继续锁定，直到有非付费获取说明页或正式商店决策。禁止把关键突破材料改成只能用灵石买。
- **主路径**：backend、admin、client、docs
- **验收**：来源消耗表与代码一致；新号不充值也能完成第一阶段闭环；+ 号仍提示暂未开放。
- **依赖**：无
- **优先级**：P1
- **风险**：葫芦是另一套未开放货币，不要偷偷拿来当第二灵石。

### CNT-12 今日目标（轻量日常，不做断签惩罚）

- **状态**：部分完成（仅洞府每日阵图）
- **玩家目标**：每次打开游戏，主界面或可到达入口能看到 3 件「今天值得做的事」，做完有小奖励，不做也不会被惩罚。
- **做法**：例如：领取离线、完成一次挂机关卡或迷雾战斗、领取洞府产出、完成阵图、强化一次。奖励用已有资源（精粹、种子、灵石小额、修为丹）。配置放后台，按服务器日切（已有 `progress/day.ts`）。**禁止**：连续登录才能突破、体力隔日清零、限时绝版成长。
- **主路径**：backend、client、admin
- **验收**：日切后刷新；补领规则明确（建议不可隔日补，但昨天没做不扣成长）；奖励走权威发放。
- **依赖**：CNT-11 的资源表
- **优先级**：P1
- **风险**：这不是完整任务系统。不要同时做周常、通行证、签到日历。

### CNT-13 纪事 / 图鉴骨架

- **状态**：缺失（长线设计有见闻、图鉴，传承要保留它们；当前没有玩家可回看的图鉴页）
- **玩家目标**：打过的首领、见过的功法、探索过的地点能再看一眼，给长线一个「收集」感，并为以后传承做数据准备。
- **做法**：先做只读图鉴：已遭遇首领、已获得功法、已探索迷雾图。数据可从 `player_stage_progress`、`player_skills`、`player_fog_runs` 推导，必要时加 `player_codex`。入口放在修炼或洞府子页，不占底栏。不需要先做传承。
- **主路径**：backend、client
- **验收**：新遭遇自动点亮；未遇的只显示剪影或「尚未见过」；不泄露未开放内容的数值。
- **依赖**：无
- **优先级**：P2
- **风险**：为传承预留字段即可，不要提前做重置。

### CNT-14 传承预览（只做预览，不开放执行）

- **状态**：缺失
- **玩家目标**：在接近第一阶段终点时，能看到「将来传承会保留什么、重置什么」，但现在还不能误点清空角色。
- **做法**：按 ADR-0005 列出保留项与重置项的配置草案，在突破或洞府最深层给只读预览。**不提供确认执行、不写重置代码到可调用接口。** 等 OPEN-04 批准再做真正传承。
- **主路径**：docs、admin、client
- **验收**：界面明确写「尚未开放」；不存在可把境界清零的玩家接口。
- **依赖**：CNT-13
- **优先级**：P3
- **风险**：这是高风险系统。预览文案必须与未来实现一致，否则会损害信任。

## 6. 第三阶段：体验打磨与留存

目标：同样的系统，看起来、听起来、打起来像一款可给人玩的游戏，而不是灰盒加占位。官方美术按生产规范重做，不把废弃或未合格素材包装成正式资源。

### ART-01 官方战斗角色动画生产规范与第一批主角

- **状态**：缺失（正式合格的攻击序列不存在；预览工具已有）
- **玩家目标**：主角在战斗里有可读的待机、普通攻击（起手–命中–收势）、受击，风格统一，透明背景，脚底稳定。
- **做法**（先规范，后制作，再考虑接入）：
  1. 产出制作规格书，建议与已有流水线计划对齐并按现状修正：画布 / 格子（历史合同曾用 640×320、脚底 `(240,280)`，预览页检查格亦为 640×320；竖屏战斗舞台以 1080×2340 为准，脚底对齐 `combat_cast.gd` 的站位比例）、PNG 序列、每帧 30–400ms（现默认约 83ms）、动作表（至少 idle / attack / hit，建议同时规划 cast、skill、down、victory）、禁止绿幕误抠、源人物高度需足够以免放大发糊。
  2. 明确当前动作表（`game/anim_q/battle_runtime/art/hero_sheet.png` 切片）仅为占位，许可未核验，**不得当作正式资源发布**。
  3. 第一批只做**一个主角的一套普通攻击循环**（含待机与受击）。敌人、完整技能剑气、场景后景分开立项。
  4. 制作流程建议：锁定镜头与角色比例 → 每动作单独片段 → 抽帧到草稿预览页检验穿帮、多肢、脚滑、破洞 → 负责人验收。验收前不写入 `animation_packs`，不进游戏包。
- **主路径**：art、admin、docs
- **验收**：规格书经负责人确认；第一批序列在战斗预览草稿中能完整播放普通一击；穿帮清单清零或列为已知限制；许可与署名写入 `docs/art/asset-register.md` 与 `ASSETS_LICENSES.md`。
- **依赖**：FND-07；接入游戏依赖 OPEN-01
- **优先级**：P0（规范与启动），制作本身是关键路径
- **风险**：禁止用 AI 临时生成一套「看起来像官方」的攻击帧直接进 `res://`。预览通过 ≠ 可以上线。

### ART-02 章节战斗背景与界面氛围

- **状态**：部分完成（有确认稿底板与部分章节背景字段，后段复用）
- **玩家目标**：不同章节的战斗和关卡页能分辨地点。
- **做法**：按 8 章出竖屏背景规范（安全区避开顶栏底栏、不要干扰角色脚底）。先做前三章正式稿，后五章可先色稿。登记许可证。
- **主路径**：art、admin、client
- **验收**：前三章在真机 1080×2340 上不遮挡血条与按钮；缺资源时有明确占位，不粉红丢图。
- **依赖**：CNT-02 的章节定名
- **优先级**：P1
- **风险**：注意刘海与底部手势条安全区。

### ART-03 敌人与首领造型

- **状态**：部分完成（首领有 artKey / 特效字段；实战怪物大量复用熊王静图 + 代码动作）
- **玩家目标**：至少能区分小怪、精英、章末首领，而不是同一只熊换血量。
- **做法**：每个新增造型先出静姿 + 受击色；动作序列可后于主角。问心谷三只怪应各有静姿。继续禁止用主角表冒充怪物帧。
- **主路径**：art、client、admin
- **验收**：问心谷三怪与炼气章首领在战斗中可辨；缺失时提示或灰度占位，不串模。
- **依赖**：ART-01 的格子规范应复用
- **优先级**：P1
- **风险**：工作量大于主角第一批，按章分期，不要一次承诺全部 24 首领全动作。

### ART-04 技能特效与命中节奏对齐

- **状态**：部分完成（九套 Q 版特效已有，剑气 / 爆炸有占位帧；许可与品质待审）
- **玩家目标**：放技能时能看懂元素类型，命中爆点与掉血时间一致。
- **做法**：在正式角色动画接入后，用入战预览（经 OPEN-01 批准的那种）校对 `skill_impact_delay()`。未接入前，只整理现有 FX 的许可、尺寸和过度遮挡问题，不重写战斗公式。
- **主路径**：art、client
- **验收**：九种 `fx_type` 仍能映射到特效；命中时刻与服务器日志一致；无许可证的资源不得进正式包。
- **依赖**：OPEN-01（若要做入战对齐预览）
- **优先级**：P2
- **风险**：改动画时长不得改掉血时间。

### ART-05 洞府与迷雾场景美术

- **状态**：部分完成（问心谷有换皮；洞府曾去掉精画底 / 地标 / 水火特效，设施以可玩灰盒 + 部分 FX 为主）
- **玩家目标**：洞府看起来像居所经营，迷雾看起来像可走的谷地，而不是纯列表。
- **做法**：恢复或重做洞府总览氛围（仍保持四入口清晰可点），不要用特效挡住领取按钮。迷雾第二图与问心谷保持同一套物件规范（`level_objects.json` 一类元数据）。
- **主路径**：art、client
- **验收**：入口可发现性不低于现在；低端机不过度填满粒子。
- **依赖**：可与 CNT-07 并行
- **优先级**：P2
- **风险**：历史提交特意去掉过重装饰，复加时要对比可玩性，而不是只堆氛围。

### ART-06 图标、头像、应用图标替换

- **状态**：部分完成（大量 Q 版图标已进包，状态多为待审核；应用图标为几何占位）
- **玩家目标**：图标可识别、风格一致，商店截图与桌面图标不是临时几何图形。

### ART-07 音频：音乐与音效第一批

- **状态**：缺失（无音频文件；只有总线开关）
- **玩家目标**：打开音乐能听到安全的循环 BGM（或明确的静音态）；突破成功、战斗命中、领取、按钮有短音效。关开关立即生效（已有 `LocalSettings.apply_audio()`）。
- **做法**：准备可商用的短循环与 8–12 个 UI / 战斗音效，放入游戏资源并登记许可。播放器把 bus 设为 `Music` / `SFX`。默认音量合理，首次进入遵守开关默认开但不要突然爆音。没有语音也可以。
- **主路径**：art、client
- **验收**：开关能静音对应总线；后台切回前台不叠多个 BGM；无许可的音源不得入库。
- **依赖**：无
- **优先级**：P1
- **风险**：循环音的内存与 Android 音频焦点（来电时应变静音或暂停）。

### ART-08 全库美术 / 字体许可审计

### UX-01 设置页「更多」信息与合规入口

### UX-02 战报、伤害数字与战斗可读性

### UX-04 低端机性能与电量

- **主路径**：client

## 7. 第四阶段：发布就绪（不是已经要求正式上线）

目标：当负责人决定发测试包或以后上架时，技术与合规已经准备好。**本阶段任务默认仍在本机或指定测试通道验证。** 未单独要求前，不执行正式环境部署、不切换共享库、不改真实玩家数据。`dev2` 测试服已在文档中出现，使用时必须明确是测试包通道。

### REL-01 打包、签名、版本号纪律

- **状态**：部分完成（有 `export_presets.cfg`、`tools/release/*`、`tools/deploy/release_apk.sh`、Android updater 插件）
- **玩家目标**：安装包能装、能覆盖、versionName 与 versionCode 同步递增。
- **做法**：整理一份给外部团队的打包手册：密钥存放（不得进 Git）、`versionCode` 必须严格增加、`dev` 包与 `dev2` 测试包标识（applicationId）差异、禁止把测试服 URL 写回仓库。打完后用现有 `verify_*` 脚本做冒烟。
- **主路径**：tools、docs、client
- **验收**：手册可独立执行；一次本地或测试通道出包，安装后设置页版本号正确；仓库里的 `project.godot` 仍是 127.0.0.1。
- **依赖**：FND-01
- **优先级**：P1
- **风险**：Android 不允许普通应用静默覆盖安装，更新流程必须保留系统确认页。

### REL-02 更新通道与兼容

- **状态**：部分完成（更新清单、提示、下载、校验、PackageInstaller 已有；多份历史 CDN / Releases 地址并存于 README）
- **玩家目标**：从旧测试包能收到更新提示并安全升级，不会把存档写成不兼容再静默清空。
- **做法**：核对当前真正使用的 update.json 通道，删掉文档里的过时地址或标为历史。确认服务器 `versionCode` 检查与强制更新开关。回归「更新时有未结算战斗 / 未领取洞府」的行为。
- **主路径**：client、backend、docs
- **验收**：低 versionCode 会被提示；取消更新仍可进入（除非强制更新）；进度仍在。
- **依赖**：REL-01
- **优先级**：P1
- **风险**：旧 0.6.x 本地存档按 ADR-0007 **不迁入账号**。文档要对玩家和测试者说清：新版本是账号进度，不是旧单机档。

### REL-03 安全基线（无运营后台扩张）

- **状态**：部分完成（有限流插件、密码哈希、会话、HTTPS 在正式方案中待运维；开发是明文 HTTP 本机）
- **玩家目标**：测试环境不被随意刷注册、刷结算；密码不以明文存。
- **做法**：审查限流是否在 `/api/v1` 与登录接口生效；检查日志脱敏（已有 `logRedact`）；测试环境管理员密码不得用默认值对外暴露。规划正式环境 HTTPS、备份、密钥保管，但**只出方案，不在未授权时实装到公网**。B 阶段的封号、多管理员、回滚仍不做。
- **主路径**：backend、docs
- **验收**：安全说明列出已有控制和已知缺口；默认口令不会出现在给外部的公开文档截图里（本文也只引用本机默认，并要求首次启动即改）。
- **依赖**：无
- **优先级**：P1
- **风险**：本机默认管理员密码只用于本机。

### REL-04 可观测性与基础质量数据（非商业分析包）

- **状态**：缺失
- **玩家目标**：出了崩溃或卡死，开发能知道发生在哪，而不是先给玩家「再装一次」。
- **做法**：先接崩溃与 ANR 日志（需选择可在中国大陆合法使用、且隐私政策覆盖的方案，或先做本机日志导出）。打点只覆盖技术事件：启动、登录失败、结算失败、战斗 recover、更新失败。不要做广告 ID 画像。正式产品分析需 OPEN-06。
- **主路径**：client、backend、docs
- **验收**：人为制造一次结算失败，能在日志中定位请求 id（后端已有 `x-request-id`）；客户端有导出或上传开关。
- **依赖**：UX-01 / OPEN-05
- **优先级**：P2
- **风险**：未同意隐私政策前不要上传设备信息。

### REL-05 内容发布流程从「保存即生效」走向可发布

- **状态**：部分完成（有草稿表、快照、版本历史和体检，但导航文案写明「开发阶段保存即生效，无需再点发布」；玩家读当前配置表）
- **玩家目标**：以后多人本机或测试环境改表时，不会把半成品数值立刻打到正在玩的号上——这要等负责人决定切换时机。
- **做法**：先写清当前实际行为与目标行为（ADR-0006 / 0007：草稿 + 不可变发布快照）。给出切换清单：哪些写接口仍直接改生效表、战斗预览如何继续隔离、测试号如何指向已发布快照。未经批准不要在共享环境打开「保存即生效」。
- **主路径**：backend、admin、docs
- **验收**：文档与代码注释一致；若尚未切换，界面必须继续明白写「开发期立即生效」；战斗预览仍除外。
- **依赖**：OPEN-07
- **优先级**：P2
- **风险**：过早切换会打乱现在单人调参效率；过晚则无法多人协作。

### REL-06 测试包验收清单与回滚

- **状态**：部分完成（有设备验证脚本、更新校验；缺少对外的一页纸验收）
- **玩家目标**：每次出测试包都用同一标准签收。
- **做法**：把 FND-10 剧本 + 更新 + 权限（安装未知应用）+ 性能抽测做成签收表。写清测试包失败时如何回退到上一 versionCode，而不动数据库（APK 回退 ≠ 内容回滚；内容回滚是 B 阶段且当前明确未做）。
- **主路径**：docs、tools
- **验收**：签收表随包；未通过不得宣称「可玩版本已发布」。
- **依赖**：FND-10、REL-01
- **优先级**：P1
- **风险**：不要用正式玩家库做回退试验。

### REL-07 商店物料与应用信息（仅准备）

- **状态**：缺失
- **玩家目标**：若以后上架，名称、简介、年龄分级、截图、权限说明已准备，而不需要临时截几张灰盒。
- **做法**：准备应用名「修仙」、包名、短简介（放置修仙，不承诺尚未存在的宗门或付费内容）、隐私政策链接、截图规范。不在本任务内提交商店审核，除非另有授权。
- **主路径**：docs、art
- **验收**：物料包齐全且与真实功能一致，无虚假系统宣传。
- **依赖**：ART-06、UX-01
- **优先级**：P3
- **风险**：简介不要写抽卡、PK、跨服。

### REL-08 iOS 与多平台（明确后置）

- **状态**：缺失（产品目标提到 iOS，当前发布渠道是 Android APK 热更）
- **玩家目标**：无（本阶段不对玩家承诺 iOS）。
- **做法**：只保留风险说明：Godot 导出、更新机制（iOS 不能按现有 APK 覆盖安装）、登录与支付合规都要另案。不要在本清单实施。
- **主路径**：docs
- **验收**：文档写明「未启动」。
- **依赖**：OPEN-08
- **优先级**：P3
- **风险**：把 Android 更新代码假设为 iOS 可用。

## 8. 建议实施顺序

下列顺序按依赖和风险排列，供外部团队做迭代计划。每一迭代都应该留下可玩的 `dev`，而不是长时间不可运行。

1. **交接周**：FND-01、FND-02、FND-07、FND-09、ART-08（许可盘点启动）、FND-11 摸底。先能跑、先分清预览草稿和游戏。
2. **闭环可教**：FND-03、FND-10、FND-04、FND-05、FND-08、FND-06。目标是新号能被人带着或自己走通。
3. **内容加厚第一波**：CNT-03、CNT-04、CNT-11、CNT-02、CNT-01（分批开闸）、CNT-12 + RET-01。
4. **秘境与功法**：CNT-07、CNT-08、CNT-05、CNT-06、CNT-09、CNT-10。
5. **表现与听觉**（可与 3–4 并行，但接入游戏必须等 OPEN-01）：ART-01 规范与制作、ART-06、ART-07、ART-02、ART-03、UX-02、UX-04、RET-02。
6. **长线预埋但不开启**：CNT-13、CNT-14（只读）。
7. **测试包就绪**：REL-01、REL-02、REL-03、REL-06、UX-01、REL-05 方案。REL-04、REL-07 按需要。
8. **明确后置、等待决策**：付费、邮件、兑换码、商品订单、宗门、排行、斗法、聊天、抽卡、法宝 / 灵宠、真正的传承执行、iOS、正式环境部署。

人力资源建议：策划 / 数值与程序可以先做第 2–4 步；美术从 ART-08 与 ART-01 规格立即开始，不要等程序把预览接到游戏里才开工。

## 9. 非目标与必须向负责人确认的未决事项

外部团队**不得假设**下列事项已经批准。需要书面决策后再单独立项。

### 9.1 非目标（当前不要做）

- 复制任何竞品的名称、文案、数值表、地图名、功法名、美术或代码。
- 把战斗预览草稿发布、上线或同步进游戏（除非 OPEN-01 批准）。
- 把未合格或许可未核验的动作表，宣称为官方正式攻击动画。
- 在 `dev` 上对正式 / 共享数据库执行迁移、清档、补发；未要求时不跑正式部署脚本。
- 真实支付、广告换关键产出、付费加速（ADR-0005 / 分期 B）。
- 抽卡（gacha）或用随机商城替代现有掉落与炼器。
- 邮件、礼包、兑换码、商品订单（后台侧栏已标为 B 阶段灰色文字）。
- 封号、版本内容回滚、多管理员权限（B 阶段）。物品锁定曾被 A 阶段明确去掉，不要擅自加回。
- 宗门 / 门派多人、排行榜、论剑斗法、跨服、聊天、道侣。
- 无限随机重铸、把未审核脚本放进内容包。
- 断签惩罚、真实时间过期的关键成长、限时绝版成长、开局强制飞升重置。
- 第六底栏，或与修为 / 历练无关的孤立小游戏。
- 新的本地权威结算。
- 旧 0.6.x 单机档自动迁入账号（ADR-0007：不迁）。
- iOS 上架与静默安装。

### 9.2 开放决策（OPEN）

**OPEN-01 战斗预览何时、以何种方式接入游戏。**  
当前决定是：只在后台看表现。将来若接入，应单独验收主角正式序列，走明确发布步骤，缺帧报错不静默降级，并处理与历史 `animation_packs`「保存即生效」接口的关系。未批准前禁止接入。

**OPEN-02 账号体系。**  
现在只有用户名 + 密码，没有邮箱 / 手机找回。是否做绑定、是否允许改名、是否允许多设备同时在线，需要决定后再实现。

**OPEN-03 法宝、灵宠格子。**  
A 阶段已预留、第三期开放。开放前要有获取、养成、战斗接入和美术，禁止先放空格子当可玩系统。

**OPEN-04 传承 / 飞升执行。**  
设计已有，代码不可执行。首次开放窗口原设想偏 Day 21–35，需按现在的 24 层节奏重估。必须可恢复快照、可拒绝传承。

**OPEN-05 用户协议、隐私政策、年龄分级与客服渠道。**  
上架和任何日志上报的前置。文本与责任方不在代码里。

**OPEN-06 产品分析与运营指标。**  
技术崩溃日志 ≠ 运营分析。留存、漏斗是否做、用哪家服务、是否在大陆可用，需单独决策。

**OPEN-07 何时结束「开发阶段保存即生效」。**  
关系到多人同时配表和测试环境稳定性。切换前要有已发布快照被客户端真正读取的确认（分期文档已提醒这一点）。

**OPEN-08 发布通道。**  
当前：本机 `dev`；测试包 `dev2` + 文档中的测试服。商店上架、正式服、域名与 HTTPS、是否继续 GitHub Releases / jsDelivr 热更，均未在本文授权实施。

**OPEN-09 离线上限是否从 8 小时提高。**  
长线设计希望至少容纳一天间隔，但 8 小时是已有基线。改上限会影响留存和数值，需负责人确认。

**OPEN-10 葫芦货币、邮件、商店「+」号。**  
界面已按设计稿展示并锁定。是永久删除，还是留到 B 阶段再用，要明确，以免玩家以为游戏坏了。

**OPEN-11 「无名修仙录」对照对象。**  
未能核到确切官方页。若必须对标，请给出官方介绍链接后再补任务。

**OPEN-12 付费与商业化。**  
分期规定真实支付另行决定。在此之前不要做首充、月卡、战斗内购。
